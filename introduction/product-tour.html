Product tour

Shield Astra has six screens the compliance function touches daily. The easiest way to understand the product is to follow one transaction all the way through — from ingestion to STR filing. That's what this page does.

The path of one transaction​

Imagine a UAE PSP customer sends AED 55,000 to a beneficiary in Türkiye (a FATF grey-list jurisdiction). Here is what Shield Astra does with that transaction, and which screen shows what.

Step 1 — Ingestion (no UI screen)​

The PSP's core system sends the transaction to Shield Astra's Ingestion API as JSON:

POST /v1/ingestion/fiat_transfer
{
  "object_id": "tx_2026_08_17_00001",
  "customer_id": "cust_123",
  "amount_aed": 55000,
  "receiver_country": "TR",
  "is_cross_border": true,
  "purpose_code": "PRP",
  ...
}

This happens in milliseconds. No screen involved — this is system-to-system.

See Data Model › Ingesting data.

Step 2 — Scenarios & Rules (Scenarios page)​

The transaction hits the Fiat Transaction Monitoring scenario. All 66 fiat rules evaluate against it. In this example, three rules fire:

  • Very-large cross-border transfer (+10)
  • FATF Increased Monitoring receiver country (+10)
  • CBUAE FTS reporting threshold (+5)

Total score: 25.

The Scenarios page shows the scenario, its rule list, and each rule's formula in a visual builder. You can preview any rule against sample data before publishing.

See Scenarios & Rules › Executing a scenario.

Step 3 — Decisioning (Decisions page)​

Score 25 lands in the Block and Review band (10 ≤ score < 30). A decision record is written with the outcome, the score, and every rule that fired. The decision goes to the workflow layer.

The Decisions page lists every decision with filters (scenario, outcome, date range) and drill-down to each decision's rule-by-rule breakdown.

Step 4 — Case creation (Case Manager)​

A workflow rule attached to the scenario says "if outcome ∈ {Review, Block-and-Review, Decline} → CREATE_CASE in AML Reviews inbox." A case is created and appears in the analyst's inbox.

The Case Manager page shows the inbox with a list of open cases, the detail view for each case with the transaction, the customer, the rules that fired, and controls to comment, snooze, escalate, close, or set an outcome.

See Case Manager › Overview.

Step 5 — AI Case Review + Continuous Screening (Case detail)​

Inside the case, the analyst clicks Generate Review. In ~9 seconds the AI narrative appears — a 7-section compliance review structured the way the MLRO set it up (Executive Summary, Customer Profile, Transaction Facts, Red Flags, Prior History, Recommendation, Evidence Checklist).

At the same time, the customer is being continuously screened against OpenSanctions and the UAE Local Terrorist List by the background worker. If a hit appears, a second case of type continuous_screening is created and linked to the customer.

See Case Manager › AI Case Review and Continuous Screening › Overview.

Step 6 — Analyst decision + goAML filing (Compliance runbook)​

The analyst reviews, adds a comment, escalates to the MLRO. The MLRO determines an STR is required and follows the goAML filing runbook. The STR reference number is recorded on the case; the case closes with outcome confirmed_risk and status closed.

See Compliance › UAE STR/SAR Filing.

The screens in the sidebar​

Following the transaction above, here is where each daily screen sits in the UI's left sidebar:

  • Scenarios — design + publish scenarios and their rules
  • Continuous Screening — configure and monitor sanctions/PEP screening
  • Lists — manage the custom lists rules reference (FATF grey list, sanctioned wallets, etc.)
  • Decisions — audit trail of every decision the engine has made
  • Case Manager — the compliance analyst's inbox
  • Screening Search — ad-hoc name / entity search against sanctions
  • Analytics — dashboards of decision outcomes, rule performance, FP rate
  • Your Data — the ingested data model (customers, accounts, transactions, etc.)
  • Settings — AI, KYC, screening, and inbox admin

What webhooks are

A webhook is Shield Astra's way of pushing events into your own systems as they happen — with no polling on your side. Every time something interesting happens inside the product — a transaction is scored, a case is created, an analyst reviews a decision, a case is tagged, a comment is added — Shield Astra fires an HTTP POST at a URL you provide, carrying a JSON payload that describes what happened.

You use webhooks to keep your core banking system, your case-management SIEM, your MLRO's Slack / Teams channel, or your goAML export pipeline in step with what's happening inside Shield Astra — without any of those systems having to ask.

Why your Webhooks page is empty right now​

Open Settings → Webhooks on a fresh install and the list is empty. That's the correct default — Shield Astra ships with zero webhooks configured. The webhook gateway (Convoy) that runs underneath is up and ready to deliver events; it just has no destinations yet.

You add webhooks by clicking + New webhook and pointing each one at a URL your team owns. Empty until you fill it — the same way the Users page is empty until you invite users.

The ten event types Shield Astra ships with​

Every webhook can subscribe to one, some, or all of these. Leave the event-types field empty when you create a webhook to subscribe to all events.

Event typeWhen it firesCommon consumer
decision.createdEvery time a transaction is scored (Approve / Review / Block-and-Review / Decline)Your core banking system — so it knows whether to release, hold, or decline the payment
case.created_manuallyAn analyst opened a case by handCase-management SIEM
case.created_from_workflowThe workflow layer opened a case automatically (e.g. score landed in Block-and-Review)MLRO Slack / Teams
case.updatedAny change to a case object (status, assignee, inbox, …)Case-management SIEM, goAML export runner
case.decisions_updatedDecisions attached to a case changedCase-management SIEM
case.decision_reviewedAn analyst reviewed a decision inside a caseMLRO Slack, quality-assurance dashboards
case.tags_updatedCase tags changedCase-management SIEM
case.comment_createdA new comment was added to a caseMLRO Slack, case-management SIEM
case.file_createdA file / attachment was added to a caseDocument management system
case.rule_snooze_createdAn analyst snoozed a rule on a caseRule-tuning tracker

How to add a webhook​

Settings → Webhooks → + New webhook — fill in three fields:

  1. URL — the endpoint your side exposes, e.g. https://core.example.ae/omnis-tm/decisions. Must be HTTPS in production.
  2. Event types — pick from the ten above. Leave empty to subscribe to all events.
  3. Signing secret — Shield Astra generates one; copy it. Every payload sent to your URL arrives with an HMAC-SHA256 signature in the X-Convoy-Signature header, computed against this secret. Your receiver verifies the signature and rejects anything that doesn't match — that's how you prove a payload really came from Shield Astra and not somebody who guessed the URL.

Save. From that moment, the next matching event triggers an HTTP POST at the URL you gave.

What a payload looks like​

Every payload is JSON, delivered as an HTTP POST with Content-Type: application/json. A decision.created event looks like:

{
  "event": "decision.created",
  "event_id": "01HNAJ8Q9RSN6PY4A8SXZQZK4T",
  "timestamp": "2026-08-19T09:14:22Z",
  "data": {
    "decision_id": "dec_2026_08_19_00042",
    "object_id": "tx_2026_08_19_00042",
    "scenario_id": "sce_fiat_tm",
    "scenario_name": "Fiat Transaction Monitoring",
    "iteration": 9,
    "outcome": "Block-and-Review",
    "score": 25,
    "case_id": "case_2026_08_19_00007",
    "trigger_object_type": "fiat_transfer"
  }
}

Signature header sent with every request:

X-Convoy-Signature: t=1755589662,v1=5f8b1c9d4e2a…

t is the delivery timestamp, v1 is HMAC_SHA256(signing_secret, "{timestamp}.{body}") in hex. Reject any request older than 5 minutes or where v1 doesn't match — that closes the replay-attack window.

Retry, rate-limit, dead-letter — you get all this for free​

The webhook gateway (Convoy) handles delivery robustness for you:

  • Retry on failure — any non-2xx response is retried with exponential backoff, up to a configurable number of attempts (default 6, spread over ~24 hours)
  • Rate limit per endpoint — configurable requests-per-second per webhook, so a burst of activity in Shield Astra doesn't hammer your receiver
  • Dead-letter queue — after retries are exhausted, the delivery lands in a DLQ visible on the webhook's Deliveries tab, with the full request + response captured for debugging
  • Idempotency — every payload carries a unique event_id. Store it on your side and skip repeats

Testing webhooks during UAT (no domain, no real receiver)​

If you're on a UAT / pilot stack and haven't wired up any real destination yet — no core-banking URL, no MLRO Slack, no goAML runner — you can still exercise the full webhook feature. You need two things:

1. A place to POST at (the receiver). Open webhook.site in a browser. It gives you a unique URL like https://webhook.site/8a3f2b1c-9d4e-4b7a-…. Copy that URL. Every HTTP POST to it shows in a live inbox on the same page, with the full headers and JSON body. No signup, no charge. This is your stand-in receiver.

2. A place to watch what was sent (Convoy admin UI). The webhook gateway inside Shield Astra is Convoy. Its admin UI is exposed on port 5006 of the server running the product — open http://<your-server-hostname>:5006 in a browser and log in with the Convoy bootstrap credentials from your operator (CONVOY_ADMIN_USERNAME / CONVOY_ADMIN_PASSWORD in the deployment .env). This shows every event Shield Astra fired, every delivery attempt Convoy made, and the response the receiver returned.

The 5-minute demo flow for testers​

  1. Open webhook.site — copy the unique URL it shows you
  2. In Shield Astra → Settings → Webhooks → + New webhook
  3. Paste the webhook.site URL, leave Event types empty (subscribes to all events), save. Copy the signing secret.
  4. In Shield Astra → open a transaction that triggers a decision, or open a case and add a comment
  5. Switch to the webhook.site tab — the event appears in the inbox within a second, with the full JSON payload and the X-Convoy-Signature header
  6. Switch to http://<server>:5006 — the same event shows in Convoy's admin UI with a green 200 OK next to it

That's the whole feature demoed end to end without needing a domain, an integration, or a receiver of your own. The moment your real receiver exists, you edit the webhook and swap the URL — every other setting stays.

What testers should look for​

  • The event fires within a second of the action that caused it
  • The webhook.site inbox shows a signature header that matches the signing secret Shield Astra generated
  • Convoy's admin UI shows 200 OK for that delivery, and the payload matches what webhook.site received byte-for-byte
  • If you deliberately break the receiver (delete the webhook.site URL, or point at a non-existent host), Convoy retries with exponential backoff — visible on the delivery-attempt timeline

Common failures and how to spot them​

Open Settings → Webhooks → <your webhook> → Deliveries to see the delivery log per event:

StatusMeaningWhat to do
2xxYour receiver accepted itDone
4xx (401 / 403)Your receiver refused itCheck your signature-verification logic — the secret must match what Shield Astra shows on the webhook page
4xx (400 / 422)Your receiver rejected the payloadLog the exact body on your side and compare against the shape above
5xxYour receiver crashed / timed outThe gateway will retry; fix the crash on your side
TimeoutYour receiver didn't respond within 30 sThe gateway will retry; make your handler faster or acknowledge async
In DLQAll retries exhausted, gave upFix the receiver, then replay from the Deliveries tab

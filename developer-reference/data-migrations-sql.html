Data migrations SQL

SQL patterns for the four migration phases described in Data migrations.

Each of the four migration types (add, remove, rename, retype) corresponds to a specific SQL pattern. The rule of every one is the same — additive first, destructive later.

Add a field​

Two statements: one to alter the physical table, one to register the field.

-- Physical column
ALTER TABLE "org-<your-org-name>".customer
    ADD COLUMN edd_reason text;

COMMENT ON COLUMN "org-<your-org-name>".customer.edd_reason IS
    'Reason for EDD flag — CBUAE AML/CFT §5.';

-- Register so the UI and rule builder see it
INSERT INTO astra.data_model_fields (table_id, name, data_type, description)
VALUES (
    (SELECT id FROM astra.data_model_tables WHERE name = 'customer'),
    'edd_reason',
    'String',
    'Reason the customer was flagged for Enhanced Due Diligence.'
);

Remove a field​

Two phases. Phase 1 deprecates the field (metadata update); phase 2 removes it after the watch window.

-- Phase 1 — deprecate (hide from rule builder)
UPDATE astra.data_model_fields
    SET is_deprecated = true
    WHERE table_id = (SELECT id FROM astra.data_model_tables WHERE name = 'customer')
      AND name = 'legacy_field';

-- Phase 2 — remove after 30–90 day watch window
DELETE FROM astra.data_model_fields
WHERE table_id = (SELECT id FROM astra.data_model_tables WHERE name = 'customer')
  AND name = 'legacy_field';

-- Optionally drop the physical column
-- (Keeps SCD-2 history of the removed data if you skip this)
ALTER TABLE "org-<your-org-name>".customer DROP COLUMN legacy_field;

Rename a field​

Three phases: add the new name, backfill, remove the old.

-- Phase 1 — add the new name alongside the old
ALTER TABLE "org-<your-org-name>".customer
    ADD COLUMN nationality_iso3 text;

INSERT INTO astra.data_model_fields (table_id, name, data_type, description)
VALUES (
    (SELECT id FROM astra.data_model_tables WHERE name = 'customer'),
    'nationality_iso3',
    'String',
    'ISO-3166 alpha-3 (replaces alpha-2 `nationality`).'
);

-- Phase 2 — backfill historical rows
UPDATE "org-<your-org-name>".customer
    SET nationality_iso3 = astra.iso2_to_iso3(nationality)
    WHERE nationality_iso3 IS NULL;

-- Phase 3 — remove the old field via the two-phase remove above

Change a field's type​

Four phases: add correctly-typed field, backfill with cast, dual-write, remove old.

-- Phase 1 — add the correctly-typed field
ALTER TABLE "org-<your-org-name>".fiat_transfer
    ADD COLUMN amount_aed_v2 numeric(18,4);

INSERT INTO astra.data_model_fields (table_id, name, data_type, description)
VALUES (
    (SELECT id FROM astra.data_model_tables WHERE name = 'fiat_transfer'),
    'amount_aed_v2',
    'Float',
    'AED-normalised amount (replaces string amount_aed).'
);

-- Phase 2 — backfill with explicit cast; malformed → dead-letter
UPDATE "org-<your-org-name>".fiat_transfer
    SET amount_aed_v2 = amount_aed::numeric
    WHERE amount_aed_v2 IS NULL
      AND amount_aed ~ '^\d+(\.\d+)?$';

-- Phase 3 — dual-write in the ingestion pipeline; migrate rules

-- Phase 4 — remove the old field via the two-phase remove above

Rows where the cast fails go to a dead-letter list for compliance review — you cannot silently drop them.

Reload after SQL changes​

Click Settings → Data Model → Reload in the UI, or restart the backend, after any of the above SQL.

Migrations in CI​

If you use Alembic, place your migrations under <your-org-name>-migrations/ alongside the starter-table migrations under backend/alembic/versions/. Never edit a migration file after it has run in production — add a new migration that undoes and reapplies. Editing history breaks replay for anyone rebuilding from source.

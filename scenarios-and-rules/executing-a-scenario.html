Executing a scenario

Before we dive into how to edit a scenario, let us give an overview of what a scenario is made of and how it is executed.

A scenario is used to detect a certain type of risk, following specific business rules, for a specific triggering event. It's a named bundle of rules that evaluates one type of transaction — a fiat wire, a crypto transfer — and produces a single scored decision. Each rule inside the scenario contributes a score; the scores are summed; the total maps to an outcome (Approve, Review, Block and Review, or Decline).

Shield Astra ships with two scenarios out of the box: one for fiat transactions and one for crypto. You'll find them on the Scenarios page, reached from the left sidebar.

What happens when a scenario is executed​

Click into a scenario and you land on its versioned detail page. This page is where you:

  • See which version is currently Live — every scenario has one live version at any time
  • Look at older iterations that were live in the past (kept for replay + audit)
  • Trigger a real-time decision via the API, or run a batch execution over historical data
  • Compare two versions against the same set of transactions before publishing a new one
  • Wire up a workflow that fires when a decision on this scenario lands in a certain outcome band

The four ways a scenario can execute​

There are four ways to make a scenario run against a transaction. You'll use one or two of them depending on your operating model.

  • API execution. Your core system calls POST /v1/ingestion/<table> for each transaction as it happens. The scenario runs synchronously and the response contains the decision. This is the mode you'll use once you're live — see Send your first transaction.
  • Batch execution. Click Launch now on the scenario detail page to run the current live iteration against every row already in the table. Useful for backfills, for testing a new iteration against last month's data, or for scheduled overnight rescans.
  • Scheduled execution. Set a cron-like schedule on the scenario. Every schedule fire re-runs the scenario against transactions that arrived since the last fire. Useful for rules that need a rolling look-back window.
  • Manual execution. From the scenario detail page, run the scenario against a single object by ID. Useful when investigating a specific case.

Only one live scenario per table​

At any moment, exactly one scenario is Live per trigger table. When you edit a live scenario, your changes go into a new draft — the live version keeps running against production traffic until you publish the new iteration. This is what makes tuning safe: an experimental change never touches live decisions until you deliberately promote it.

See Lifecycle for how draft → test → publish works.

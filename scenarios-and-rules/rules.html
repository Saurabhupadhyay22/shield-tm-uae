Rules

Every rule is authored in the visual builder. Pick a field, pick an operator, pick a value, set a score. Publish. No SQL, no code.

Here's the Rules tab inside the Fiat TM V9 Live iteration:

A rule in one line

IF <field> <operator> <value> THEN add <score> points.

Compose many of these with AND / OR to make a compound rule.

Anatomy of a rule​

Authoring — click by click​

  1. Scenarios → open scenario → New rule
  2. Name the rule — Sanctioned PEP sender. This becomes the tag on decisions.
  3. Add a condition:
    • Field: transaction.customer.pep_status
    • Operator: IS TRUE
  4. Add a second condition (AND):
    • Field: transaction.customer.sanctions_status
    • Operator: IS TRUE
  5. Set the score — +15.
  6. Save as draft. The rule doesn't fire on live transactions yet.

Test it against sample data (Testing rules) before publishing.

The field picker​

The field picker walks the data model links. Dot-navigation from the current table outward:

transaction                          ← the fiat_transfer row itself
transaction.customer                 ← the sending customer (via link)
transaction.customer.pep_status         ↑ any field on that customer
transaction.customer.nationality
transaction.account                  ← the debit account
transaction.beneficiary              ← the receiving beneficiary
transaction.beneficiary.bank_country
  • Scalar field
  • Linked field
  • Aggregate

Read a value on the current table.

transaction.amount_aed > 50000

Cheap — no join.

Walk a link to another table.

transaction.customer.pep_status = true

Join happens once per decision; cached across rules in the same scenario run.

Compute over a rolling window. See Aggregations.

SUM(transaction.amount_aed WHERE customer_id = current.customer_id
    WITHIN LAST 30 DAYS) > 500000

Expensive — use sparingly, or move to a scheduled scenario.

Full detail per type in Field types.

Custom lists in rules​

Whitelists, blocklists, high-risk-corridor lists, sanctioned-wallet lists. Reference them in a rule with IN:

transaction.receiver_country IN "FATF Grey List Countries"
transaction.beneficiary.bic IN "Blocked BIC List"

See Using lists in rules.

Performance guidance​

If your scenario is over the 400ms budget

Reach for these in order:

  1. Reorder rules cheapest-first. A rule that reads transaction.amount_aed fires before one that reads transaction.customer.pep_status — cheaper join.
  2. Deduplicate joins. If 8 rules reference transaction.customer.*, they share one join. If they reference transaction.customer.owner or other nested paths, each is its own join.
  3. Move aggregates to scheduled scenarios — see Aggregations.

What happens on publish​

The scenario becomes a new iteration (Publishing an iteration). The previous iteration is archived and remains available for replay.

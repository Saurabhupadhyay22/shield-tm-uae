Duplicating for tuning

Tuning is normal — false-positive rates drift, corridor risk shifts, new regulations land. The rule you shipped 90 days ago isn't the rule you need tomorrow.

Never edit a live rule in place

Duplicate first. Edit the copy. Test the copy. Keep the winner. The live rule stays untouched until the winner is approved.

The tuning loop​

Step-by-step​

  1. Scenarios → open scenario → find the rule → ⋮ menu → Duplicate
  2. The copy is named <original name> (draft) and lives in the same scenario, disabled.
  3. Edit the copy — change the threshold, tighten the condition, adjust the score.
  4. Test the copy against the last N days of decisions. The simulator shows: how many more/fewer cases the copy would produce, which specific past decisions would have flipped.
  5. Submit for approval, marking the copy as the replacement for the original. On approval, the original is disabled and the copy is enabled — atomic swap.

Common tuning patterns​

  • Threshold tuning
  • Condition tightening
  • Score re-weighting

Rule: Very-large cross-border transfer — currently fires at amount_aed > 100,000, +10 points.

Problem: Too many Review cases on legitimate corporate wires.

Tune: Duplicate. Change threshold to amount_aed > 250,000. Test.

Expected: Same catch rate on high-risk wires (they're mostly over AED 250k anyway), 30% fewer FP cases.

Rule: FATF grey list receiver — currently fires on any receiver in a grey-list country.

Problem: UAE-resident customers legitimately send remittances to grey-list home countries (Türkiye, Vietnam, Philippines).

Tune: Duplicate. Add AND transaction.customer.country_of_residence != transaction.receiver_country. Test.

Expected: Drops the remittance-cluster false positives.

Rule: KYC stale (> 12 months) — currently +5 points.

Problem: Firing constantly but rarely correlating with real risk.

Tune: Duplicate. Change score to +2. Test.

Expected: Same total case count, but stale-KYC alone no longer pushes a transaction into Block-and-Review.

Deprecating a rule outright​

Sometimes the answer is "delete this rule". Two-phase, like a schema change:

  1. Duplicate the rule, mark the duplicate as disabled = true.
  2. Watch the disabled rule for 30 days. Confirm no legitimate hits are lost.
  3. Remove the disabled rule via Submit for approval → remove.

Naming conventions​

Copies get (draft) suffixed. Renames survive publication. Once a copy replaces the original on publish, drop the (draft) — you can rename the winner to just the rule's canonical name.

Common naming shapes:

  • Very-large cross-border transfer — the live rule
  • Very-large cross-border transfer (draft) — the tuning copy
  • Very-large cross-border transfer — v2 (2026-08 tuning) — a disambiguated draft for a specific reason

Multi-rule tuning in one iteration​

You can duplicate three rules, edit all three, and submit them as one iteration. Approvers see them as a bundle. This is the right shape for a quarterly review — one approval, three tuned rules, one audit event.

What the reviewer sees​

The MLRO's review page shows:

  • Every duplicated rule side-by-side (live vs draft)
  • The specific fields changed (highlighted)
  • The FP-delta from the simulator
  • The reviewer can approve rule-by-rule or all-at-once

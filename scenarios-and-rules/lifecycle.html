Lifecycle

Every published change is a new iteration. This page walks the flow from a draft edit to the moment it starts scoring live transactions.

Here's the top of a scenario detail page:

Iterations, not overwrites

The current live scenario is never modified in place. Every change becomes a new iteration; the previous iteration is archived and stays available for replay. This is what makes rollback safe.

The flow​

Step-by-step​

  • Author (Analyst)
  • Approver (MLRO)
  • Engine
  1. Scenarios → open live → Duplicate → New iteration
  2. Edit rules (Rules)
  3. Test against last-24h historical decisions (Testing rules)
  4. Submit for approval — enter a change reason (goes on the audit record and the release note)
  1. Scenarios → Pending approval shows submissions
  2. Review the diff: rules added, rules removed, rules edited, band changes, expected FP delta
  3. Read the change reason and the test-replay results
  4. Approve or Reject (with a comment). Approval writes an audit row with your identity.
  1. On approval, the engine:
    • Archives the current live iteration
    • Marks the approved iteration as live
    • Reloads the rule cache
  2. The next ingested transaction hits the new iteration.

Zero downtime. The changeover is atomic — no transaction sees a half-loaded iteration.

Rollback​

If the new iteration causes a spike in false positives, an over-block, or a rule that fires unexpectedly:

  1. Scenarios → open live → Iteration history
  2. Find the last known-good iteration
  3. Restore — creates a new iteration cloning the old one, marks it as pending approval
  4. MLRO approves — the restored version is now live

Rollback follows the same approval flow as any other change. No "emergency" bypass. This is intentional — the audit trail should never have a gap.

Approval routing​

By default, any live change requires MLRO approval. Configuration options:

Change typeDefault approverConfigurable
Rule condition editMLROYes — can require MLRO + Head-of-Compliance
Rule weight edit ≤ 10%Compliance LeadYes
Rule weight edit > 10%MLROYes
Band editMLRO + Head-of-ComplianceYes
New rule addedMLROYes
Rule removedMLRO + Head-of-ComplianceYes
List value add / removeCompliance LeadYes

Set per-org in Settings → Governance.

Release notes​

Each iteration auto-generates a release note visible to every user with the Compliance Reader role:

Fiat Transaction Monitoring — Iteration 27
Published 2026-08-17 by Ahmed Al Falasi (MLRO)

Changes:
  + Added rule: "Emirates ID nationality vs residence mismatch" (+5)
  ~ Adjusted rule "Very-large cross-border transfer": threshold
    AED 100,000 → AED 75,000
  - Removed rule: "Legacy MCC 5993 flag" (unused since 2026-06)

Change reason:
  MLRO review post-CBUAE inspection findings 2026-Q2.

Test-replay result:
  Additional cases: +12 / day
  Additional Approve → Review shifts: +8 / day
  No FP-rate regression on live-shadow window.

Formula reference

Every rule compiles to an Abstract Syntax Tree. Most authors never see it — the visual builder produces the AST for you. But when you export a rule for review, backup, or programmatic edit, this is what you see.

You don't need this page day-to-day

If you're just writing rules in the builder, skip to Aggregations. This page is the reference for exporters, integrators, and reviewers.

Example — a real rule, as JSON​

{
  "name": "Very-large cross-border transfer to grey-list country",
  "score": 10,
  "condition": {
    "type": "Logical",
    "op": "AND",
    "operands": [
      {
        "type": "Comparison",
        "op": ">=",
        "left": {"type": "FieldRef", "path": "transaction.amount_aed"},
        "right": {"type": "Literal", "value_type": "Float", "value": 100000}
      },
      {
        "type": "Comparison",
        "op": "IS_TRUE",
        "left": {"type": "FieldRef", "path": "transaction.is_cross_border"}
      },
      {
        "type": "Comparison",
        "op": "IN",
        "left": {"type": "FieldRef", "path": "transaction.receiver_country"},
        "right": {"type": "ListRef", "list_name": "FATF Grey List Countries"}
      }
    ]
  }
}

Validation​

The AST validator runs on every save. It catches:

  • Type mismatches — comparing a Bool with >
  • Unknown fields — transaction.nonexistent
  • Unknown lists — IN "list I haven't created"
  • Missing operands — AND with one child
  • Circular references — a rule that includes itself

Errors show inline in the visual builder before you can save the rule.

Export / import​

Every scenario exports as JSON:

GET /v1/scenarios/<id>/export

Roundtrip-safe. Import into a lower environment with:

POST /v1/scenarios/import
Content-Type: application/json
{...exported JSON...}

Field paths must resolve on the target — matching table names + registered fields required.

Ingesting data

How and why to ingest data. Interfaces and formats.

Once your data model is defined, your rules can only run against data that's been ingested into it. Ingestion is how your core system tells Shield Astra about a new customer, a new account, or a new transaction. Every ingested payload is validated, versioned, and stored — and for transaction tables, ingesting also triggers the scenario engine and returns a decision in the same response.

The value of Shield Astra is that, once your data has been ingested — or rather, is being continuously ingested — the tool abstracts away the tedious work of building aggregates, indexes, and history tables in your own code. Every rule sees the current row, and every rule can look back at previous versions of the same object.

When to ingest​

You should ingest a record whenever your core system creates it or updates it. The typical pattern is a webhook or an outbound event from your core system that fires an ingestion call in real time:

  • A new customer completes KYC → POST /v1/ingestion/customer
  • An account is opened → POST /v1/ingestion/account
  • A customer initiates a fiat wire → POST /v1/ingestion/fiat_transfer — this returns a decision your core system uses to release, hold, or decline the payment
  • The customer's PEP status changes at your next screening refresh → POST /v1/ingestion/customer again with the new pep_status — a new version of the customer row is created

You don't need to send everything through the same endpoint or all at once — customers are typically ingested first (from your KYC system), then accounts, then transactions as they happen.

How it works​

Each of the tables in your data model has its own endpoint. The endpoint name matches the table name — POST /v1/ingestion/customer, POST /v1/ingestion/fiat_transfer, and so on.

The request is a JSON object with one key per field on the table. object_id is required (it's the natural key). updated_at is required. Everything else depends on how you configured the table.

API is the preferred method

Ingestion by API is the preferred method — it lets you have the freshest data available for your decisions at any given time. Batch upload from a CSV is also supported for historical backfills, but real-time transactions should go through the single-record endpoint.

Sending a customer​

curl -X POST https://<your-host>/v1/ingestion/customer \
  -H "X-API-Key: $ASTRA_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "object_id": "cust_123",
    "full_name": "Ahmed Al Falasi",
    "date_of_birth": "1990-05-14",
    "nationality": "AE",
    "country_of_residence": "AE",
    "emirates_id_number": "784-1990-1234567-1",
    "kyc_status": "VERIFIED",
    "pep_status": false,
    "sanctions_status": false,
    "risk_score": 22,
    "risk_band": "LOW",
    "is_active": true
  }'

The response comes back immediately:

{
  "status": "ok",
  "object_id": "cust_123",
  "valid_from": "2026-08-17T09:14:22Z"
}

Resending the exact same payload is a no-op — the response returns the same valid_from and nothing is written. Resending with a change (say, pep_status: true) closes the current row and opens a new version.

Sending a transaction​

Transaction tables (like fiat_transfer and crypto_transaction) behave the same way, but with one important addition: ingesting a transaction triggers the scenario engine and returns a scored decision in the same response.

curl -X POST https://<your-host>/v1/ingestion/fiat_transfer \
  -H "X-API-Key: $ASTRA_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "object_id": "tx_2026_08_17_00001",
    "transaction_date": "2026-08-17T09:14:22Z",
    "customer_id": "cust_123",
    "account_id": "acct_456",
    "beneficiary_id": "ben_789",
    "amount": 55000,
    "currency": "AED",
    "amount_aed": 55000,
    "sender_country": "AE",
    "receiver_country": "TR",
    "is_cross_border": true,
    "purpose_code": "PRP",
    "transfer_type": "SWIFT",
    "status": "PENDING"
  }'

The response includes the decision:

{
  "status": "ok",
  "object_id": "tx_2026_08_17_00001",
  "decision": {
    "outcome": "Block-and-Review",
    "score": 25,
    "scenario": "Fiat Transaction Monitoring",
    "rules_fired": [
      { "name": "Very-large cross-border transfer", "score": 10 },
      { "name": "FATF Increased Monitoring receiver country", "score": 10 },
      { "name": "CBUAE FTS reporting threshold", "score": 5 }
    ],
    "case_id": "case_2026_08_17_042"
  }
}

Your core system reads decision.outcome — one of Approve, Review, Block-and-Review, or Decline — and acts on it (release the payment, hold it, decline it).

Every decision — from every ingested transaction — shows up on the Decisions page in the UI, so an analyst can inspect any decision after the fact.

Idempotency​

Ingestion is idempotent by object_id. Sending the same payload twice results in one row. Sending a changed payload with the same object_id creates a new version — the old version is preserved.

For safety on retries, you can also set an Idempotency-Key header. Any request with the same key within 24 hours returns the cached response without re-evaluating the scenario.

Batch ingestion (for backfills only)​

Historical backfills go through a batch endpoint:

POST /v1/ingestion/<table_name>/batch
  • Up to 500 records per call
  • Does not run the scenario engine — it's for populating history only
  • If any object within a batch is rejected, the entire batch is rejected

Real-time transactions must go through the single-record endpoint.

Common failures​

If a call returns a non-2xx status, the full HTTP status matrix (rate limits, backpressure, idempotency semantics) lives in the developer reference — ingestion failure modes. The two most common causes for day-to-day operators are:

  • 401 / 403 — the API key is missing, wrong, or lacks the INGESTION_WRITE scope. Rotate from Settings → API keys.
  • 422 — a field's type doesn't match the payload. See Field types.

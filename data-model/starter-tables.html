Example data model

The following is the data model Shield Astra ships with. It's designed to be sufficient for a first implementation of AML and fraud rules for a UAE PSP or VASP, without requiring you to build a schema from scratch. You can reuse it as-is, extend it, or replace it with your own.

The model has eight tables. Two describe who (customer, corporate_customer), three describe where money sits or moves to (account, beneficiary, merchant), two describe what actually moved (fiat_transfer, crypto_transaction), and one records screening signals attached to those actors (screening_result).

customer​

The individual customer profile. One row per real person. Every KYC refresh or PEP re-check creates a new version of the row; the old version is retained.

Key fields your rules will reach for:

  • full_name, date_of_birth, nationality — identity (FATF R.10 §5(a))
  • emirates_id_number, visa_type — UAE-specific (CBUAE §3.4)
  • country_of_residence — geographic risk
  • pep_status, pep_jurisdiction — politically-exposed person status (FATF R.12)
  • sanctions_status — populated by the continuous-screening worker (FATF R.6, R.7)
  • kyc_status, kyc_last_refreshed_at — for KYC-stale rules
  • risk_score, risk_band — composite 0–100 rating
  • source_of_funds, annual_income_aed — Enhanced Due Diligence (FATF R.10 INR §5)

Links out to account (as owner), fiat_transfer and crypto_transaction (as sender), and screening_result (as subject).

corporate_customer​

A business entity — company, partnership, sole trader, trust. Feeds every rule that references a corporate counterparty.

Key fields:

  • legal_name, trading_name — identity
  • registration_number, incorporation_country — Know Your Business
  • industry_sector, mcc — sectoral risk
  • ubo_name, ubo_ownership_pct — Ultimate Beneficial Owner (FATF R.24, ≥25% threshold)
  • kyb_status — one of PENDING / VERIFIED / REJECTED / EXPIRED
  • sanctions_status, pep_association — entity + associated PEPs
  • annual_revenue_aed — source-of-wealth checks

Governed by FATF R.24–25 (Beneficial Ownership), CBUAE §3.5 (KYB), and VARA CRMR Part III for VASP corporate CDD.

account​

A payment instrument. Fiat or crypto — the account_type field discriminates.

Key fields:

  • customer_id — the owner (link to customer)
  • account_type — CURRENT / SAVINGS / WALLET / CRYPTO_WALLET / CUSTODY
  • currency — ISO-4217 for fiat, BTC / ETH / USDT / … for crypto
  • iban, bic — fiat identifiers
  • blockchain_address, chain — crypto identifiers
  • balance — latest known
  • status — ACTIVE / FROZEN / CLOSED

beneficiary​

The receiving party on an outbound transfer.

Key fields:

  • full_name (FATF R.16 §2(a))
  • bank_name, bank_country, bic — beneficiary institution
  • iban or account_number — receiving account
  • is_sanctioned — populated by screening
  • relationship_to_sender — SELF / FAMILY / BUSINESS / UNKNOWN

merchant​

Merchant reference — used on card, e-commerce, and acquiring flows. Optional; empty for pure PSP-to-PSP transfer businesses.

Key fields:

  • merchant_name
  • mcc — ISO-18245 Merchant Category Code, for MCC-based risk rules
  • country, acquiring_bank — corridor risk
  • is_online — e-commerce vs card-present
  • risk_level — LOW / MEDIUM / HIGH

screening_result​

One row per screening event. Written by the continuous-screening worker every time OpenSanctions, the UAE Local Terrorist List, or an adverse-media API is queried against a customer.

Key fields:

  • customer_id — the subject of the screening
  • screening_type — SANCTIONS / PEP / ADVERSE_MEDIA
  • data_source — OPENSANCTIONS / UAE_LOCAL_TERROR_LIST / …
  • matched_entity_name — human-readable match
  • match_score — 0.00 to 1.00
  • match_status — HIT / POTENTIAL_HIT / FALSE_POSITIVE / CLEARED
  • reviewed_by, reviewed_at — disposition audit trail

fiat_transfer​

A fiat transaction. SWIFT wire, SEPA, local ACH, remittance. This is what your fiat scenarios evaluate.

Key fields:

  • customer_id, account_id, beneficiary_id — links
  • amount, currency, amount_aed — the last one is used for threshold rules (AED-normalised so a rule works for any currency)
  • sender_country, receiver_country — corridor rules
  • sender_bic, receiver_bic — SWIFT institution rules
  • is_cross_border, is_high_risk_corridor — set at ingestion
  • purpose_code — CBUAE list (links to ref_purpose_codes)
  • transfer_type — SWIFT / SEPA / LOCAL / REMITTANCE / INTERNAL
  • status — PENDING / COMPLETED / FAILED / REJECTED / REVERSED

Governed by FATF R.16 (wire transfers), CBUAE FTS Notice 6/2019 (Fund Transfer System), and the CBUAE RPSCS Regulation.

crypto_transaction​

An on-chain crypto transfer. This is what your crypto scenarios evaluate, and it carries the FATF Travel Rule payload for VASP-to-VASP transfers.

Key fields:

  • customer_id, account_id — links
  • asset_type — BTC / ETH / USDT / USDC / …
  • amount_crypto, amount_usd, amount_aed — native + USD + AED
  • blockchain_network — BTC / ETH / TRX / SOL / …
  • from_address, to_address, tx_hash — on-chain identifiers
  • counterparty_vasp_name, counterparty_vasp_jurisdiction — for VASP-specific rules
  • mixer_detected, high_risk_address_flag — Chainalysis / TRM signals
  • chainalysis_score, risk_score — composite risk
  • is_defi — DeFi contract interaction
  • travel_rule_required, travel_rule_compliant — FATF R.16 INR §7 (≥ USD/EUR 1,000)
  • travel_rule_ivms101 — the IVMS-101 JSON payload itself

Governed by FATF R.15 (VASP obligations), FATF R.16 INR §7 (Travel Rule), VARA CRMR Part III (crypto CDD), and the VARA Custody Services Rulebook Part IV.

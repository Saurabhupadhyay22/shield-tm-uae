Field types

The five field types and how each one maps to the ingestion API.

Every field in Shield Astra is exactly one of five types: String, Bool, Int, Float, Timestamp. This is a deliberate design choice — the rule builder shows every field in one click, and the compliance officer authoring a rule never needs an engineer to explain a type.

Picking a type​

  • Yes/no or true/false → Bool
  • Money, percentage, score with decimals → Float
  • Whole-number count → Int
  • A moment in time → Timestamp
  • Anything else → String

String​

The default for anything that isn't obviously one of the other four. Names, identifiers, codes, enums, addresses, JSON blobs (as a string), IBANs, wallet addresses.

  • Whitespace is preserved. Case is preserved.
  • Empty "" is stored as an empty string, not NULL.
  • JSON null is stored as SQL NULL.
  • Maximum length is 65,535 characters.

Common mistake: treating a numeric code as an Int. MCC codes, ISO-3166 country codes (including the numeric ones like 784), and phone numbers all look numeric but are codes, not quantities. Store them as String. Never do arithmetic on them.

Bool​

For simple true/false values — is_active, pep_status, is_cross_border.

  • JSON true or false is stored.
  • "true" or "false" as a string is rejected (HTTP 422). Coerce client-side before sending.
  • 1 or 0 as an integer is rejected. Send actual booleans.
  • JSON null is stored as SQL NULL.

Booleans are strict on purpose — silent-fail rules were the common failure mode when we accepted "true".

Int​

For whole-number counts — number of accounts, number of previous transactions, a risk score from 0 to 100.

  • Range is -9,223,372,036,854,775,808 to +9,223,372,036,854,775,807 (Postgres bigint).
  • 42.0 (a decimal) is rejected. Use 42 or the Float type.
  • "42" (a string) is rejected.

Float​

For anything with decimals — money amounts, percentages, scores.

  • Precision is 4 decimal places. 0.12345 is stored as 0.1235 (banker's rounding).
  • For crypto amounts that need 18-decimal precision, use a pair of fields: amount_crypto as Float for rule evaluation, plus amount_crypto_raw as String with the exact value for settlement.
  • "55.4" (a string) is rejected.

Timestamp​

For a moment in time. ISO-8601 with an explicit timezone offset is required.

Accepted:

  • "2026-08-17T09:14:22Z" (UTC)
  • "2026-08-17T13:14:22+04:00" (Dubai time with offset)

Rejected:

  • "2026-08-17T09:14:22" — no offset, ambiguous
  • "2026-08-17" — date-only, no time
  • "1723886062" — Unix epoch, not accepted

Stored internally as timestamptz (UTC), displayed in the organisation's timezone (default Asia/Dubai).

Common mistakes​

  • Rule amount > 10000 never fires — the field is stored as String, not Float. Change the type (see Data migrations) and re-ingest.
  • Rule pep_status IS TRUE never fires — the ingestion payload is sending "true" as a string, not the JSON boolean true. Fix on the caller side.
  • Cross-border flag is always NULL — the payload omits the key entirely. Send false explicitly for the "not cross-border" case.
  • A timestamp is off by four hours — the timezone offset is missing. Include +04:00 or Z.

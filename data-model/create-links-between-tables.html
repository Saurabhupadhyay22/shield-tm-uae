Create links between tables

How to create links between tables. How they are used. Things to keep in mind.

A rule that says "block when the sender is a sanctioned PEP transferring to a high-risk country" has to reach across four tables. Links are how it does that without SQL, without joins, and without the rule author having to know either.

What a link is

A link is a directed pointer from a field on one table to a field on another table. In the rule builder, it becomes dot-navigation — transaction.customer.pep_status walks the link from fiat_transfer to customer and reads a field on the resolved customer.

Links are similar to database foreign keys, but they are not implemented as concrete foreign keys. You define them once, and every rule can walk them without joining.

An example speaks louder than a theoretical description. Consider the data model shipped with Shield Astra — every fiat wire, fiat_transfer, refers to two other entities: the customer sending it (via customer_id) and the beneficiary receiving it (via beneficiary_id). Both relationships need to be crossable in a rule.

Creating a link​

To create a link from your table to another table, open the source table on the Your Data page. In the field list, find the field that already holds the reference (typically an _id field such as customer_id). Click + Create a link on that field.

The link editor asks for two things:

  • Link name — a short label. The convention is <from_table>_<to_table> — for example card_transaction_customer. This is the label that shows up in the rule builder.
  • Target table + field — the parent table you're linking to, and the field on it you're targeting. In almost every case, the target field is the parent's object_id (its natural key).

Click Save. Rule authors can now type card_transaction.customer. and see every field on the resolved customer.

Reading a link in a rule​

Once a link exists, the rule builder walks it as dot-navigation:

transaction.customer.pep_status = true
  • transaction — the current fiat_transfer row
  • .customer — walks the link (customer_id → customer.object_id)
  • .pep_status — reads the field on the resolved customer

You can chain scalars but not links — transaction.customer.nationality is one link + one scalar. Chained links (transaction.customer.owner.parent) are supported but every level is another lookup; two levels is the pragmatic ceiling.

Historical links​

Both sides of a link are versioned. When a rule evaluates a transaction from January 2026, and the customer has since had their PEP status updated in May 2026, the engine walks the link using the version of the customer that was valid when the transaction happened, not the current one.

This is what makes rule replay possible. A scenario re-run against last year's transactions gives the same answers today that it gave at the time. See Record retention and history for how the versioning works.

Modelling cardinalities​

A link must point unambiguously from a child to a parent — one child row has exactly one parent through this link. That covers 1:1 and N:1 relationships directly.

For 1:N relationships (one customer has many transactions), the link goes on the child (fiat_transfer.customer_id → customer.object_id). To reach the many transactions from a customer, you use an aggregation — "sum of fiat_transfer.amount_aed where customer_id = this.customer_id in the last 30 days".

For N:N relationships (a customer has multiple accounts, an account has multiple authorised users), model an intermediary table with one link to each side.

Things to keep in mind​

  • The target field should be the parent's object_id. Linking to a non-natural key means multiple parent rows can match — that's a bug and rules will resolve inconsistently.
  • A dangling reference doesn't error at ingest. If you ingest a fiat_transfer with customer_id = "cust_999" and no such customer exists, the ingest succeeds. The rule that references transaction.customer.pep_status simply doesn't resolve — score contribution is 0, and the decision detail marks the rule field unresolved. This is intentional — in some cores, transactions arrive before their customers.
  • You can filter rules on "customer exists". Combine with transaction.customer.object_id IS NOT NULL if the rule should only fire when the customer is known.

Managing your schema through CI? The SQL equivalent for registering a link lives in the developer reference — data model SQL.
